# 评测能力维度定义

fuckcode eval 把工程能力分成**两大类、六个维度**。每个维度有明确的测什么、怎么判定、出题指南。

## 分类总览

```
确定性任务（硬判定：单元测试 exit 0）
├── algorithm/       算法/逻辑
├── data-structure/  数据结构
├── parsing/         解析/字符串
└── bugfix/          Bug 定位修复

开放式任务（软判定：多维度 rubric + LLM-judge）
├── architecture/    架构/系统设计
└── requirements/    需求分析/业务设计
```

---

## A. 确定性任务

特点：**有标准答案**，用单元测试的 exit code 判定。0 或 1，没有中间地带。

### algorithm/ — 算法/逻辑

**测什么**：逻辑推理、算法实现（排序/搜索/DP/贪心/数学）

**判定方式**：`bun test` / `pytest` / `go test` exit 0

**出题要点**：
- 测试用例必须覆盖边界（空输入/单元素/负数/极大值）
- 不要只测 happy path，要测 edge cases
- 难度由算法复杂度和边界用例数量决定

**现有任务**：
| ID | 语言 | 难度 | 内容 |
|----|------|------|------|
| `algo-ts-binary-search` | TS | easy | 二分查找 |
| `algo-py-merge-intervals` | Python | medium | 合并重叠区间 |
| `algo-go-fizzbuzz` | Go | easy | 可配置 FizzBuzz |

### data-structure/ — 数据结构

**测什么**：数据结构的工程实现（链表/栈/队列/树/图/哈希表），考验指针/引用维护、不变量保持

**判定方式**：单元测试 + 有时配 behavior 断言（验证 class 结构存在）

**出题要点**：
- 测试要覆盖结构性操作（插入后结构正确、删除后指针不断）
- 删除操作要测三种场景：删叶子/删中间节点/删根
- 多轮混合操作能验证不变量

**现有任务**：
| ID | 语言 | 难度 | 内容 |
|----|------|------|------|
| `ds-ts-linked-list` | TS | medium | 泛型双向链表 |
| `ds-py-binary-tree` | Python | medium | 二叉搜索树（含删除） |

### parsing/ — 解析/字符串

**测什么**：格式解析、字符串处理（CSV/JSON/TOML/正则/编码转换）

**判定方式**：单元测试

**出题要点**：
- 格式规范要给清楚（RFC 摘要或简化规则）
- 测试用例覆盖所有转义/引用/嵌套边界
- 这是 bug 高发区，测试要狠

**现有任务**：
| ID | 语言 | 难度 | 内容 |
|----|------|------|------|
| `parse-ts-csv` | TS | medium | CSV 解析器（引号/转义/跨行） |
| `parse-py-toml` | Python | hard | 简易 TOML 读取器 |

### bugfix/ — Bug 定位修复

**测什么**：读代码找 bug 的能力、根因分析

**判定方式**：单元测试（含之前失败的回归测试）

**出题要点**：
- 初始代码要能跑（有 bug 但不是语法错误）
- bug 类型多样：off-by-one/资源泄漏/竞态/空指针/类型错误
- prompt 只给"有 bug，找出并修复"，不告诉 bug 在哪

**现有任务**：
| ID | 语言 | 难度 | 内容 |
|----|------|------|------|
| `bugfix-ts-off-by-one` | TS | easy | 分页 off-by-one |
| `bugfix-py-async-leak` | Python | medium | 异步资源泄漏 |

## B. 开放式任务

特点：**没有唯一标准答案**，用多维度 rubric + LLM-as-judge 判定。每个维度独立打分，按权重加权。

这部分是业界**空白点**——SWE-bench/Aider 全是"给需求写代码"，没人测架构设计和需求拆解。

### architecture/ — 架构/系统设计

**测什么**：系统设计能力——分层、解耦、可扩展性、接口抽象、设计权衡

**判定方式**：`multi-rubric`（4 个维度：可扩展性/正确性/接口设计/文档质量）

**出题要点**：
- 多轮引导（分析需求→设计接口→实现核心→文档）
- 评分标准聚焦"设计决策"而非"代码量"
- 最关键的维度通常是可扩展性（策略模式/中间件链用得好不好）

**现有任务**：
| ID | 难度 | 内容 | 核心考察能力 |
|----|------|------|-------------|
| `arch-ts-design-cache` | hard | 缓存系统设计 | 策略模式/淘汰策略抽象 |
| `arch-ts-design-api-gateway` | hard | API 网关设计 | 分层/中间件链/解耦 |

### requirements/ — 需求分析/业务设计

**测什么**：需求拆解、API 设计、任务分解——把模糊需求变成可执行的东西

**判定方式**：`multi-rubric`（4 个维度：规范性/完整性/类型设计/文档质量）

**出题要点**：
- 产出主要是文档/类型定义（不是功能代码）
- 评分标准聚焦"完整性"和"粒度合理性"
- 测的是产品思维/工程拆解能力

**现有任务**：
| ID | 难度 | 内容 | 核心考察能力 |
|----|------|------|-------------|
| `req-ts-api-design` | medium | 博客 RESTful API 设计 | RESTful 规范/资源关系/类型设计 |
| `req-ts-decompose-feature` | medium | 功能拆解为任务列表 | 拆解粒度/依赖关系/验收标准 |

## 如何扩充任务

1. **选维度**：决定测哪个能力（参考上面的定义）
2. **定判定**：确定性任务用 test；开放式用 multi-rubric（定义好维度和权重）
3. **写测试**：确定性任务的核心是测试用例质量——边界覆盖越全，评测越准
4. **定 rubric**：开放式任务的核心是维度定义——维度要互斥、criteria 要具体
5. **校验**：用 `safeParseTask` 验证 JSON 格式
6. **冒烟**：先 `--no-cleanup` 跑一遍看产出是否合理
7. **录制**：`--record` 存一份基线，以后 `--replay` 零成本回归

## 文件命名约定

```
<语言前缀>-<任务描述>.task.json
```

语言前缀：`ts` / `py` / `go` / `rs`（rust）/ `java`

例：`ts-binary-search.task.json`、`py-merge-intervals.task.json`
